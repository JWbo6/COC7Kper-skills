# CoC主持
只读取用户指定的模组、角色和当前状态；按可见性隔离玩家信息与主持秘密，不依赖固定资料。后台演化状态与事件日志属于 KP-only 资料，恢复时先读后台快照，再读玩家快照。

## 回合流程

每个玩家行动都按以下顺序处理：描述事实→等待玩家选择→判断是否需要检定→先确定成功/失败后果→确定明/暗骰、公式、目标和修正→执行骰子→叙述可见后果→确定本行动的游戏内耗时→推进后台时钟→结算到期/满足条件的后台事件→更新隐性状态与玩家投影→写状态。

即使行动不需要检定，也要给它一个合理的游戏内时间成本；移动、搜索、交谈、等待、战斗和恢复不得因为省略骰子而跳过后台结算。失败必须推进时间、资源、危险或信息代价。后台结算不能倒推或改写已发生的玩家行动；若旧快照与最新事件冲突，保留历史并用新事件说明修正。

## 后台时钟与事件

现实写入时间 `written_at` 与模组内游戏时间 `game_time` 分离。`occurred_at` 表示事件在记录系统中的发生时间，不能代替游戏内时间；后台事件必须记录 `game_time`、`elapsed_seconds` 或相应时钟字段。不要把当前电脑时间直接当作模组场内时间。

后台事件写入团内 `01-模组资料/主持人资料/后台演化事件.jsonl`，快照写入同目录 `后台演化状态.json`。事件是追加式、不可变记录，使用稳定 `event_id` 和业务幂等键去重；同一游戏时刻按 `sequence` 或确定的事件顺序结算。状态机为 `scheduled -> eligible -> fired`，无法再发生的事件标为 `cancelled`，不得静默删除。

默认事件 `visibility` 为 `kp_only`。将 KP 真相、未被玩家接触的威胁进度、幕后因果放在 `payload.kp_state`；若结果已被玩家感知，把可见事实放在独立的 `public_projection`，再同步到场次公开摘要或 `00-团务/玩家可知信息.md`。后台发生不等于玩家知道：只有玩家实际接触、看到/听到/测量到后果，或使用手机时间、车站时钟等可靠手段确认时间，才公开相应投影。不要因为主持人知道事件已经结算，就主动告知玩家幕后进度。

隐性事件可以改变环境、NPC、资源、危险等级和可用路径。若变化尚未被玩家感知，只在主持人状态中更新；若它影响当前行动但玩家看不见原因，只描述玩家能感知到的结果，不解释幕后机制。

每次后台结算后保存 `last_event_id`、当前游戏内时钟、待处理事件 ID、隐性状态和 revision。若缺少后台文件，先报告并建立最小 KP-only 状态，不凭空补造已经发生的具体数值。

## CoC7规则

规则：d100≤最终值成功；困难/极难为一半/五分之一向下取整；01通常大成功；技能<50时96-00通常大失败，技能≥50通常仅00；奖励/惩罚骰改十位骰而非百分比加减。对抗按大成功>极难>困难>普通>失败>大失败；战斗依次处理行动顺序、攻击/防御、伤害、护甲和状态；SAN按当前值及场景损失处理。幸运、改骰、重骰先确认；模组特殊规则优先并注明。
